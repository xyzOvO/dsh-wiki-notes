# 阶段 5：读取一致性、观察闭环与实战验收

> 本轮只做三件事：量一次「两套读取到底差在哪」、把观察闭环接上、拿五类真实问题压一遍。
> 判据与检索打分一行没动（除抽取补齐的两处：字数对象词、表格行借用页面标题）。

## 一、页面读取一致性（`eval_read_parity.py`）

对比两条真实链路：

- JS：`node bin/cli.mjs page <页名> --root <库> --chars 20000`（`lib/corpus.js` + `lib/engine.js`）
- Python：`context_builder.read_page()`

抽样：五个目录各 3 页 + 含代码块/表格的页补足，共抽 20 页，其中 15 页有可比正文。逐项比较规范化正文（CRLF→LF、行内空白压缩、去空行）、截断、章节集合、结构元素计数（标题/表格行/代码围栏/wikilink/callout）、frontmatter 类型。报告：`_tools/eval/READ-PARITY.md`。

### 结果

| 维度 | 结论 |
|---|---|
| 正文 | **逐字一致（15/15）** |
| 结构元素计数 | 一致，0 差异 |
| 截断 | 本批样本都在 6000 字以下，未触发 |
| frontmatter 列表 | **15/15 不一致** |
| sections 集合 | 2 页章节名不同（容器章节消失），其余一致 |
| 可读文件集合 | 不同（`index.md` / `log.md` / `_` 前缀） |

### 三条真实差异

1. **frontmatter 列表未解析**：Python 只做 `k, v = line.split(":", 1)`，把
   `别名: [重庆省考申论, 重庆市考申论]` 读成字符串 `"[重庆省考申论, 重庆市考申论]"`；
   JS 的 `asList()` 正常解析成数组。今天这不影响证据（证据只从正文抽），
   但别名匹配、标签过滤这类能力在 Python 侧等于没有。
2. **sections 语义不同**：JS 只按 `## `（level 2）切；Python 认 2–4 级，
   且 `sections` 只收**含正文行的章节**——纯容器章节（下面直接跟 `###` 的那种）会消失。
3. **可读文件集合不同**：`lib/corpus.js:245-246` 明确跳过 `_` 前缀、`index.md`、`log.md`；
   Python `find_page()` 全盘 rglob，`log.md` 能被当普通页读到（实测 JS `found=False` / Python `found=True`）。

### 统一方向（待拍板）

- **选项 A：以 Python 为唯一实现**，`wiki_recall` 也改读 Python 版。——彻底，但要动检索主链，风险大。
- **选项 B：Python 对齐 JS 的规范化**（解析 frontmatter 列表、跳过同三个文件名、section 只按 `## ` 切）。——改动小，不动检索。

我的建议是 **B**：正文已经逐字一致，差异全在「结构解读」，而结构解读目前只有 JS 侧在服务检索。
先把 Python 侧对齐，等以后真要合并成一份实现时，A 才有干净的地基。
两个选项都不在本轮范围内——这属于「要不要改 wiki_recall 的读取」，需要你点头。

## 二、观察闭环（`observe_id` 接通）

```
wiki_context ──► context_id（快照）+ observe_id（观察记录）
      │                    │
      └──► wiki_verify ────┴──► 追加 verify 记录（parent_observe_id 指回 context）
                                    │
                                    └──► wiki_observe 查统计
```

- 记录写在 `WIKI_OBSERVE_LOG`（默认 `_tools/eval/observe_log.jsonl`），一行一个 JSON。
- `event` 字段区分 `context` / `verify`；早期 CLI 写法没有该字段的记录计入 `legacy`，不混进统计。
- **观察是旁路**：记录失败只写 stderr，`context` / `verify` 照常返回（已验证：日志路径故意指向不可写位置，context 仍然成功且照常返回 `observe_id`）。
- **不存引文**：记录里只有「问了什么、走了哪条路、支持到哪一步、挑出了哪类违规」，没有 `quote` / `evidence` 字段。日志不是第二个库。
- **不干预回答**：观察层不拦截、不拒答、不改写，只做计数与分布。

`wiki_observe` 返回（`$defs.observe_stats`）：

| 字段 | 含义 |
|---|---|
| `totals` | `contexts` / `verifies` / `legacy` / `malformed` |
| `support_distribution` | sufficient / partial / insufficient 各多少次 |
| `retrieval_distribution` | 检索状态分布 |
| `support_reason_distribution` | 主要卡在哪类原因 |
| `violation_types` | 各违规类型被挑出几次 |
| `recent` | 最近若干条（id / 事件 / 时间 / 问题 / 状态） |

验收 `eval_observe_loop.py`：**21/21**（含跨进程查得到、追得回、计数准、不含引文、写不进也不影响主链路、两次调用不串用）。

### 插件侧接线（1.4.2 补）

上面这条闭环图在 **Python 侧**是通的，但插件侧原本断了一截：`wiki_context` 把 `observe_id` 放在返回体里，
插件既不在渲染里露出来，也不在 `wiki_verify` 请求里转发——契约里 verify 的返回体不带 `observe_id`，
Python 也不从快照回查（只认请求里带过去的那一个）。结果就是：走插件时，每条 verify 记录的
`parent_observe_id` 恒为 null，闭环在最后一跳断开。

1.4.2 的补法（Python 侧契约与实现未动）：

- 插件在 apply() 内记 `context_id ↔ observe_id` 的短期对照表（最多 64 条，换库时清空）。
- `wiki_verify` 转发时带上这一对的 `observe_id`；另开一个可选 `observe_id` 参数，显式传入时以传入的为准。
- `renderContext` 把 `observe_id` 一并输出，模型想显式传参时手里有。
- 回归门禁在 `tests/gateway.mjs`：断言 verify 记录的 `parent_observe_id` 指回 context 的 `observe_id`。

**注意**：这条修的是日志溯源，不是统计口径——`observe.stats()` 的「修正序列」本来��按 `context_id` 归组算的，
`parent_observe_id` 从头到尾没有任何统计代码消费它。

## 五、已知局限（照实写）

1. **读取仍是两套实现**——差在结构解读层，见第一节；统一方向待拍板。
2. **`unverifiable` 只在 `notices` 里**：模型若只看 `violations`，会漏掉「这个数字我核实不了」。需要模型侧读 notices。
3. **区间只支持「A–B 单位」**：`一千到一千二百字` 这类中文区间仍抽不出。
4. **`numeric_claim` 不做跨句推理**：主张散落在两句里（「作文 40 分。」「字数 1000–1200。」）时，靠整段口径继承兜底，不做句间绑定。
5. **观察日志无轮转**：只追加，不清理；`legacy` 计数会随时间变大，需要时手工归档。
6. **快照不自动清理**，也没有滑动续期。
7. **插件侧的 `observe_id` 对照表只在内存里**：插件重启后，之前的 `context_id` 查不到对应的 `observe_id`，
   这时 verify 仍能跑（核验靠快照，不靠这张表），但那条 verify 记录的 `parent_observe_id` 会是空的。
   跨进程、跨重启追不回——这是设计取舍：把编号写进快照要多动 Python 侧契约。
