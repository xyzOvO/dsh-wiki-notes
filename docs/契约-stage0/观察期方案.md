# 真实使用观察期：五个观察点怎么测

> 目标不是再验证工具对不对，而是看**模型会不会用、用了会不会改**。
> 工具能发现错误，不等于模型一定会改正错误——这是从工具可靠性走向 Agent 工作流可靠性的那一步。

## 0. 数据从哪来

三类数据，可靠性依次下降：

| 数据 | 来源 | 可信度 | 能回答 |
|---|---|---|---|
| 服务端事实 | `wiki_bridge.py` 写入的 observe 日志 | 高（自动、无自报） | 调了什么、返回什么、核验结果 |
| 会话事实 | DSH 会话记录（tool call 序列 + 模型输出） | 中（需离线对账） | 有没有调、调的顺序、模型嘴上改没改 |
| 模型自述 | 模型自己说「我查了库」 | 低 | 只能作线索 |

观察期默认**只信前两类**。日志路径由插件 `bridge.observeLog` 决定，当前是
`D:\AI库\生活库\_tools\observe\gateway.jsonl`，与自测日志
`D:\AI库\生活库\_tools\eval\observe_log.jsonl` 物理隔离——修 bug 时跑测试不会污染观察数据。

## 1. 模型是否先调 wiki_context

- **能测度**：测不到。网关没有「本轮没被调用」这个事件。
- **取数**：会话记录里逐轮看，首个 tool call 是不是 `wiki_context`；答案里出现库内事实而该轮无调用，记为「疑似绕过」。
- **判据**：出现库内可答的事实题却零调用 → 记为一次绕过。
- **已知偏差**：工具描述与系统提示会显著影响调用率；这测的其实是「提示工程 + 工具描述的合力」，不是模型单方面意愿。

## 2. 是否遵守 contract_text 的四条约束

- **能测度**：间接可测。约束要落在答案上，核验能抓一部分（必须披露缺口、不得超出证据、引文须原文）。
- **取数**：`verify` 事件的 `violation_types`；`missing.not_disclosed`、`provenance.fabricated_quote`、`weak_evidence.*` 都属这一类。
- **判据**：违规率按类型看，不看总数（不同类型发现难度差很多）。

## 3. 是否在适当时机调 wiki_verify

- **能测度**：可测，比值。
- **取数**：`stats()` 的 `totals.contexts` 与 `totals.verifies`。
- **判据**：
  - `verifies / contexts ≥ 0.6`：基本在用；
  - `0.2 ≤ 比值 < 0.6`：只在「感觉不稳」时才核；
  - `< 0.2`：基本不用，核验层形同虚设。
- **注意**：一个 context 被核验多次是好事（= 在改），别把高比值当异常。

## 4. 发现违规后模型是否修正（重点）

- **能测度**：一半。能测「重新核验后是否通过」，测不到「嘴上改了但没重验」。
- **取数**：`stats().revision`：
  - `contexts_verified`：被核验过的 context 数；
  - `corrected`：同 context 首次 fail、末次 pass —— **真改了**；
  - `unresolved`：末次仍 fail —— **改了没改对，或者压根没改**；
  - `correction_rate = corrected / contexts_verified`；
  - `sequences[]`：每个 context 的核验序列（`attempts` / `first_ok` / `last_ok` / `types_seen`）。
- **判据**：
  - `correction_rate ≥ 0.7`：核验结果被当真。
  - `0.3–0.7`：部分当真，要看 `unresolved` 的 `types_seen` 是哪类（数字类通常最容易改，披露类最难）。
  - `< 0.3`：**核验在空转**——模型看见了红字不认账。这时该改的不是判据，是提示词里的「核验结果优先」。
- **盲区（务必记住）**：只数「重验过的」。模型读了 violation 直接重写但懒得再核，会同时降低 `contexts_verified` 的可用性——表现为序列只有 1 次 attempt 且 `last_ok=false`。这种要回会话记录人工看，别直接用 `correction_rate` 下结论。

## 5. wiki_observe 能否发现长期缺口

- **能测度**：可测，但要攒量。
- **取数**：`missing[].reason` 三档（`not_found` / `not_verifiable` / `not_covered_in_wiki`）+ `support_distribution` + `retrieval_distribution`。
- **判据**：同一主题反复 `not_found` = 真缺页；反复 `not_verifiable` = 页在但证据不合格（该补来源或补结构）；`weak_only` 占比高 = 检索层单调。
- **节奏**：至少两周再聚类，一周的量看不出「长期」。

## 6. 复盘方式

每周一次，同一句：

```bash
cd D:\笔记\LLM-Wiki\工具-tools
printf '%s' '{"days":7,"limit":10}' | PYTHONIOENCODING=utf-8 python wiki_bridge.py observe
```

看四件事：`totals` 比值（第 3 点）、`revision`（第 4 点）、`violation_types` 分布（第 2 点）、`recent[].query` 里重复出现的主题（第 5 点）。第 1 点需要翻会话记录，建议每次抽 10 轮人工过一遍。

## 7. 这套观察自身的局限

1. 只覆盖「调了网关」的轮次，绕过检索的轮次天然不可见。
2. `correction_rate` 的分母是「被核验过的 context」，不是「所有出过错的回答」。
3. 日志无轮转，观察期结束要手动归档。
4. 单机单人样本，结论只对本人有效，别外推成「模型普遍行为」。
