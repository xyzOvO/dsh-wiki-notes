# 阶段 0 · 契约与现状审计

> 日期：2026-11-05 ｜ 插件：dsh-wiki-notes 1.3.0 ｜ 管线：`<你的库根目录>\工具-tools`
> 位置：本文档只做映射与判定，**不改任何检索评分、不改 engine.js、不改 Answer Policy 判据**。

## 0. 一句话结论

目标契约的字段 **90% 能直接映射到现有 `context_builder.build()` 的返回**，不需要重写判据；
真正缺的不是字段而是**三样运行期结构**（context 快照、engine 级状态、数值矛盾判据），
以及一个必须马上修的**故障可见性缺陷**（引擎报错被吞成空候选）。

## 1. 现状调用链（已核实）

```
context_builder.build(query, engines, limit)
  ├─ query_planner.plan(query)            → plan_obj: original_query / query_units / anchors / has_constraint_anchor
  ├─ run_search_py(unit_query)            → subprocess → search.py，从 stderr 的 [diag] JSON 解析候选
  ├─ run_plugin(unit_query)               → subprocess → node bin/cli.mjs search（cwd=PLUGIN）
  ├─ 页面去重（按 title）→ read_page() → extract()/extract_table_numeric()
  ├─ dedup.dedup(all_supports)            → evidence_items + dedup_stats
  ├─ conflict_check.analyze(...)          → conflicts / incomparable / compatible_pairs
  ├─ 状态三段：retrieval_status / support_status / pipeline.stage
  └─ answer_policy.policy() / check_context() / contract_text()
```

已有但未暴露的核验入口：`answer_policy.check_answer(ctx, answer, root)` —— 参数就是 **原 ctx**，
天然满足「verify 不得重新检索」。

## 3. 实测发现（用真实题包跑出来的，不是推理）

题包：`重庆 申论 考几道题`，`--engine both --limit 8`。

```
候选页 9｜候选行 24｜可读 9｜证据 5 条｜必要槽位 1（numeric）已填 1
retrieval_status=weak_only  support_status=partial  stage=ok
conflict_status=none_detected  contract_violations=[]（上下文自检通过）
```

### F1 引擎故障在输出里不可见（**必须在阶段 1 修**）

`run_search_py()` / `run_plugin()` 出错时都 `return [{"engine": ..., "error": str(exc)}]`（context_builder.py:64、109），
而 build() 第 693 行 `if "error" in c: continue` 直接丢弃。后果：

- 插件崩了/超时，输出与「插件没召回到任何页面」**字节级相同**；
- 事后无法从 ctx 重建 engine 状态，只能回看 stderr；
- 直接违背「引擎故障不得伪装成证据不足」。

修法（阶段 1，不碰判据）：在 `runs` 里额外记 `{"engine":..., "status": "error"|"timeout"|"empty"|"ok", "error": {...}}`，
`engines.*.status` 由此派生，`status.degraded=true` 时 support 不可单独采信。

### F2 「答错数字」现在抓不到（**verify 的真实缺口**）

拿同一份 ctx 快照跑三种答案（产物见 `samples/_verify_probe.json`）：

| 答案 | 结果 | 说明 |
|---|---|---|
| 「重庆申论一共考五道题，180 分钟，作文 30 分。」 | `violations_found`，仅 `weak_evidence.review_flag_missing` | **只抓到没标"需复核"，没抓到"五道题"与证据 4 题矛盾** |
| 「…4 题、150 分钟…属台账记录…需复核。」 | `ok` | 正确 |
| 含伪造引文的那句 | 抓到 `provenance.fabricated_quote` | 引文核验可用 |

原因：`numeric` 槽被填了（`filled` 里有），`missing` 为空，于是
`insufficient.answered_unfilled_slot` 不触发；管线**没有**「答案里的数值 vs 证据里的数值」比对。

结论：契约里 `unsupported_numeric_claim` 是**新增判据**，不是已有能力的改名。它必须在阶段 1 单列为
新规则（读 `ctx.evidence[].supports[].values` 与 quote 中的数值 + 槽位口径），并单测覆盖。
这也是唯一一处会让「Python 是判定中心」这句话落空的地方——不新增，verify 就只是半个核验。

### F3 support 与 stage 已独立，但 support 缺 reason

实测同时出现 `support=partial` + `stage=ok`（槽位填满但证据只到 weak）。契约需要给 support 一个
`support_reason`（如 `evidence_weak` / `slot_partial` / `conditional_only`），否则插件侧只能原样转发，
LLM 看不出"为什么是 partial"。

### F4 无 context 快照

`check_answer` 吃的是内存里的 ctx。跨进程（插件 ↔ Bridge）必须落盘快照 + TTL，否则 verify 只能重建，
也就是用户明确禁止的「第二次检索判第一次答案」。建议快照只存 `ctx` 的 evidence/supports/answer 三块
（约 40–60KB），TTL 30 分钟，过期返回 `E_CONTEXT_EXPIRED` 而不是自动重建。

### F5 子查询漂移（记录，不在本次修）

`query_planner` 把 `重庆 申论 考几道题` 拆成 `Q1 = "重庆 申论 考"`，尾部"几道题"丢失。
不致命（Q0 原句仍在），但会让 numeric 槽的关键词单元变弱。属阶段 4 评测项。

### F6 numeric 槽抽到「国考口径」行（记录）

证据 E001/E005 抽的是 `申论.md` 与 `申论·资料摘要.md` 里「180 分钟 5 题」那两行——
数字密集所以被 numeric 槽选中，与问题真正要的「重庆 4 题」是**两种口径**。
E002 抽对了（`4 题 / 150 分钟 / 100 分`）。说明抽取层还缺"口径限定词"过滤（国考/省考/重庆）。
这条属阶段 4，但**正好说明 verify 的数值判据不能只看数字相等，还要看口径标签**。

## 4. 错误码 / 超时 / 版本

### 4.1 错误码（顶层 `error`，与 `status.support` 严格分离）

| code | 触发 | retryable |
|---|---|---|
| `E_QUERY_EMPTY` | query 空/全空白 | false |
| `E_CONTRACT_VERSION_MISMATCH` | 插件与 Bridge contract_version 不等 | false |
| `E_PYTHON_UNAVAILABLE` | python 可执行文件不存在 | false |
| `E_BRIDGE_SPAWN_FAILED` | 进程起不来 | true |
| `E_BRIDGE_TIMEOUT` | 超预算（见 4.2） | true |
| `E_BRIDGE_CRASH` | 非 0 退出且无 JSON | true |
| `E_BRIDGE_BAD_JSON` | stdout 不是契约 JSON | false |
| `E_CONTEXT_NOT_FOUND` / `E_CONTEXT_EXPIRED` | verify 拿到未知/过期 id | false |
| `E_VERIFY_EMPTY_ANSWER` | verify 传空答案 | false |
| `E_ENGINE_UNAVAILABLE` | 单引擎故障（**不阻断**，只标 degraded） | true |
| `E_WIKI_ROOT_MISSING` | 库根不存在 | false |
| `E_INTERNAL` | 兜底 | false |

铁律：`error` 出现 ≠ `support=insufficient`。前者是环境故障，后者是知识结论。二者同时出现时，
以 `error` 为准，`support` 标 `unknown`（不能报 insufficient）。

### 4.2 超时预算

| 阶段 | 预算 | 超时行为 |
|---|---|---|
| plan | 1s | E_INTERNAL |
| retrieve（单引擎/单子查询） | 8s | 该引擎该单元标 timeout，其余继续 |
| retrieve 总计 | 20s | 返回已完成部分 + degraded=true |
| read+extract | 10s | 未读页记 `unreadable` |
| policy | 1s | 失败时 `answer.contract_text=""`（现有行为，保留） |
| **verify** | 2s | 纯内存读快照，超时即 E_BRIDGE_TIMEOUT |
| **observe** | 3s | 失败不影响 context 返回（现有 try/except 语义保留） |

### 4.3 版本四件套

| 字段 | 值来源 | 变更影响 |
|---|---|---|
| `plugin_version` | package.json（现 1.3.0） | 工具 schema 变 |
| `bridge_version` | wiki_bridge.py `__version__`（新） | 命令/快照格式变 |
| `contract_version` | 常量 `"1.0"` | 三者同时协商 |
| `pipeline_version` | 管线 git 短哈希或日期（现无版本） | 抽取/判据变 |

只改抽取逻辑时升 `pipeline_version`；只改工具参数时升 `plugin_version`；契约字段增删才升 `contract_version`。

## 5. 阶段 1 最小改动清单（都不重写判据）

1. `build()` 记录 engine 级 status（F1），输出 `engines` 段。
2. 把 `check_answer` 包成 CLI 子命令 `verify --context-file`，`ok→status`、rule→type 映射。
3. 新增判据 `unsupported_numeric_claim`（F2），单测先行。
4. 给 `support_status` 补 `support_reason`（F3）。
5. `wiki_bridge.py`：`context` / `verify` 两个命令，stdin/stdout JSON，stderr 只放诊断。
6. 快照目录（默认 `%TEMP%\wiki-gateway\contexts\`），TTL 30 分钟。
